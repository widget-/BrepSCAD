# Session notes — 2026-11-05

Follow-up on the OpenGrid snap cutouts. The 1x1 and 2x1 bin bodies are now
correct after the boundary-wire fix; the remaining artifacts are in the snap

## Symptom and reduction

The side clip cutout showed an upward-sloping right side and a messy wedge where
the horizontal and vertical cutouts meet. Isolated the two cutters from
`modules/snap.scad`:

- `shell`: `snap_outer_shell` alone.
- `h`: horizontal clip cutout (`prism_stack` base `[12, 0.4]`, 1.3 mm straight,
  0.2 mm at -45°).
- `v`: vertical back cutout (`prism_stack` base `[12, 0.6]`, 5.8 mm straight,
  0.3 mm at -45°).

Outer shell, `h` alone and `v` alone all match OpenSCAD exactly. The combined
subtraction is the failure:

| model | BrepSCAD | OpenSCAD |
| --- | ---: | ---: |
| `shell - h` | 3889.431265 | 3889.431265 |
| `shell - v` | 3854.706153 | 3854.706153 |
| `shell - h - v` | **3889.431265** (v dropped) | **3849.092103** |
| `shell - (h ∪ v)` | **3840.536694** (open, 92 welded boundary edges) | **3849.092103** |

The two cutters overlap by 0.4 mm in Y and 0.3 mm in Z. Their 45° end tapers
shrink the cross-section to (almost) zero, so the overlap is between two knife
edges. Moving them apart makes the result exact: `h_depth = 1.0` (0.1 mm gap)
or `v_height = 5.4` both render identically to OpenSCAD. A plain rectangular
cutout (no end taper) also gives the correct volume: `3848.376` vs OpenSCAD
`3848.361`.

## Engine failure

`BREPSCAD_DEBUG_BOOLEAN` shows the second difference returning
`EmptyOutputShell` at every tolerance, so the adapter falls back to the
unmodified subject. Stage instrumentation showed:

- `coplanar=false`, `planar_pair=true` for the `99 x 34` face pair.
- The `and` shell assembly fails: an intersection curve has two leader points
  only `~3e-10` apart. `altshell_to_shell` dedups them to one point and returns
  `None`, which aborts the whole boolean.
- The degenerate curve is at the crossing of the two knife-edge tapers. The
  raw intersection curves themselves are short but valid; the degenerate
  fragment appears after vertex insertion/cutting in the loops store.

## Attempted engine fixes (all reverted)

1. Skip intersection curves that collapse to a point in `loops_store.rs`.
   The degenerate curve was created later by vertex cutting, so the filter
   never saw it.
2. Snap near-endpoint vertices at the cut site (parameter-space tolerance
   `1e-5`/`1e-6` and a 3D `1e-6` endpoint check). This changed the result from
   "v dropped" to `3842.7`/`3828.9`, but the mesh stayed open (72–76 welded
   boundary edges) and the union path still produced a wrong shell.
3. Increase the parameter endpoint tolerance to `1e-4`: too aggressive; it
   skipped valid cuts and broke the cutter union (`4181.95`, 15 triangles).
4. Keep the raw endpoints of the degenerate curve: assembly succeeded, but the
   wrong face statuses produced wrong/open geometry.
5. Small tool shifts (`0.001`–`0.01` in X/Y/Z): no correct result; Z shifts had
   no effect, X/Y shifts changed the wrong result.

## Planar-arrangement fix

The classic loop assembly cannot represent a near-tangent intersection that
collapses to a point. A planar fallback now handles those pairs:

- `coplanar/planar.rs`: for every planar face, compute the other solid's plane
  cross-section, split the face boundary at the segment endpoints, run
  `coplanar::divide`, and classify each piece with a point-in-solid test.
  `classic::and`/`or` call it when `process_one_pair_of_shells` returns
  `EmptyOutputShell`.
- A difference is `and(subject, neg(tool))`; the negated shell has negative
  signed volume, so the point-inside result is inverted for it.
- The fallback is gated to cutout-sized operands. `small_union` uses a bounds
  volume of at most 1000 mm³; `And` also requires the tool to be at most 10% of
  the subject's bounds volume. Large model booleans keep the normal pipeline.
- The kernel checks watertightness only for small unions. If a cutout union is
  open, it falls back to a two-shell compound; the evaluator subtracts cutters
  sequentially when the union fails. This keeps the union semantics for normal
  booleans while recovering the knife-edge cutouts.

Results:

- Reduced `both` cutout: `3849.264` vs OpenSCAD `3849.09`.
- Full external `opengrid-bin.scad`: `29642.51` vs OpenSCAD `29635.87`.
- New regression test `snap_clip_cutouts_keep_the_flex_slot`, using
  `tests/data/snap_clip_cutout.scad`. The old engine drops the vertical cutout
  (`3889.43`), so the test fails there and passes with the fallback.

Remaining:

- Standalone `opengrid-snap.scad` still reports a boolean error; the full bin
  model is correct.
- The full-model mesh has 455 welded boundary edges, so it is not watertight
  yet. The fallback keeps whole faces when `coplanar::divide` reports an
  invalid cycle / interior-point failure; those cases need the remaining
  boundary T-junction treatment.
- `BREPSCAD_DEBUG_PLANAR` prints the fallback stages for future debugging.

## Practical model-level fix

leaves more open edges; the plain rectangular end is the cleanest result.

## Boolean correctness and performance pass

Started from the standalone `opengrid-snap.scad` stack overflow; ended with a
boolean performance win and a diagnosis of the remaining planar-fallback gap.
Branch `diag/planar-divide`; `main` has the correctness and performance work.

### Stack overflows

GDB backtraces named two unbounded recursions:

- `monstertruck-solid`'s `curve_surface_projection` retried by recursing. A
  degenerate intersection ran all 100 retries and overflowed the 8 MB stack.
  Now a loop; same order and result. Documented in `vendor/README.md`.
- `TruckKernel::union_shell_sets` merged shell pairs through `boolean()`, which
  re-entered the compound split once per failed fusion. A run of failures
  recursed without bound. It now calls `merge_solids` directly.

Reduced fixtures: `crates/scad-eval/tests/data/opengrid_snap/` (one and two
clips, 0.32 s and 0.69 s; the one-clip model crashes the old engine, the
two-clip model crashes an engine with only the projection fix).

### Union correctness and performance

- The compound-union fast path appended shells without checking overlap, so a
  later overlapping shape was kept twice and its volume counted twice:
  `union{A; B; C}` gave 24 instead of 18 depending on order; interleaved
  clusters gave 48 instead of 35.2. `union_shell_sets` now splits both sides
  into shells, concatenates only bounds-disjoint pairs, and fuses the rest.
- Disjoint unions use `Solid::new_unchecked`; `Solid::try_new` revalidated every
  shell and made chained unions quadratic (100-shell union 274 ms → 106 ms).
- Intersection with a compound distributes over its shells; the old path
  returned an empty solid.
- Difference cutters whose AABB misses the subject are pruned using the new
  cached `Kernel::aabb`. 100 bounds-disjoint cutters: 0.446 s → 0.143 s.
- The compound weld collapses exact duplicate attributes before the pairwise
  test. Identical cap normals and UV corners made it quadratic: a 100-shell
  compound tessellates in 71 ms instead of 3.0 s.

### Performance work

Profiling the snap model before tuning: 975 ms in 222 engine attempts, 419 ms in
13 normalized rescales, 6 ms in 15,919 projection calls. Shell-set union merges
now stop after the exact tolerances and fall back to the compound append
(`merge_solids(..., full_ladder: false)`):

| model | before | after |
| --- | ---: | ---: |
| `opengrid-snap.scad` | 1.45 s | 0.79 s |
| full `opengrid-bin.scad` | 22.5 s | 11.6 s |

Geometry is identical. Trimming difference shell splits does not change the
attempt count (their cost is exact engine work); passing either compound to
shapeops drops most of the model or empties it; subtracting cutters sequentially
panics the engine. Those routes are closed.

`scripts/check-model-metrics.sh` and `corpus/baseline-metrics.tsv` record wall
time, triangles, vertices, volume, and welded edge counts for the fixtures,
with ad-hoc baselines for the external OpenGrid models.

### Remaining planar-fallback gap

Both models still produce open meshes (239 and 404 welded boundary edges). On
the one-clip fixture the planar fallback fails 401 of 577 face divisions:

- 299 `interior_point`: the probe clearance floor `tol * 4` (0.2 mm) is wider
  than the knife-edge slivers (area 0.02–0.09 mm², longest edge 0.28–11 mm).
- 102 half-edge walk, all `used=true`: the first failing graph contains a
  zero-area boundary spike `10→11→10` of 0.053 mm, just above the `tol` vertex
  snap.

Fixing either class alone is not enough: relaxing or rescaling the probe clears
the 299 but changes volumes and adds open edges; dropping spikes clears the 102
to 11 but drifts the geometry; combining them panics the mesher. The missing
step is propagating split points across adjacent faces before sewing (the
T-junction treatment). Diagnostics are committed on `diag/planar-divide`
(`PLANAR-FAIL`, `INTERIOR-FAIL` under `BREPSCAD_DEBUG_PLANAR`).

Two things came out of re-checking the fixtures against OpenSCAD itself
(`openscad -o out.off --export-format off`, signed volume from the exported
mesh; the helper was validated on `cube(10)` -> exactly 1000):

| fixture | OpenSCAD | `main` (c6eaa01) | welded boundary |
| --- | ---: | ---: | ---: |
| `opengrid_hull_cut` | 23760.984 | 23755.314 | 37 |
| `snap_clip_cutout` | 3849.103 | 3849.275 | 69 |
| `snap_one_clip` | 1495.316 | 1502.648 | 66 |
| `snap_two_clips` | 1452.392 | 1446.002 | 127 |

`snap_one_clip` and `snap_two_clips` were asserted against BrepSCAD's own
output (1502.65, 1446.0), not against OpenSCAD; both constants came in with
`0fa10c4`, whose subject was stack-overflow coverage. They are now OpenSCAD's
values, so those two tests fail until the fallback closes the meshes. The
errors point in opposite directions (+0.49% / -0.44%), so this is not a uniform
bias that cancels.

The committed `af5d1c8` spike filter regressed the fixtures off that `main`
baseline (`snap_one_clip` 1496.18, `snap_two_clips` 1436.59), and the
uncommitted arrangement hardening on top of it was worse still
(`snap_clip_cutout` 3995.6, +3.8%). Both were dropped; the branch's engine is
`main` again.

### Why sewing the fallback result does not close it

`coplanar::sew` is the existing T-junction treatment, and calling it on the
planar fallback result is a no-op. `BREPSCAD_DEBUG_SEW` (now also reporting
`left(boundary=.. extract_ok=..)`) shows why:

- `sew` does repair the shell — 9 calls report `boundary=0 extract_ok=true`.
- 40 of the other calls compute a repaired shell and then throw it away because
  `Shell::extract` refuses it: 26 `SameVertex` (an edge whose two vertices the
  weld collapses onto each other, i.e. a zero-length edge in the fallback
  output) and 14 `NotSimpleWire`.
- A lenient extraction that drops those edges and keeps the faces
  `new_unchecked` does let the repaired shell through, but it makes `or` accept
  closed-and-wrong unions: `snap_one_clip` collapses to 539 mm3 and
  `snap_two_clips` to 512. `or`'s closedness gate is load-bearing as a sanity
  check, not just a topology check. That experiment was reverted.
- Propagating split points by splitting every edge at the vertices lying on it
  (`split::apply_splits`, keyed by `EdgeId`) also fails: it helps
  `snap_clip_cutout` (69 -> 57 open edges) and hurts both snap fixtures
  (62 -> 74, 121 -> 143), because the two faces of a T-junction hold *distinct*
  edge objects, so only one side of a coincident pair is split. Reverted.

What did land: rejecting cross-section segments shorter than `tol` instead of
`tol * 1e-3` in `cross_section_edges`, so the fallback stops emitting edges
that the weld collapses. Volumes are unchanged and open edges drop
66 -> 62 and 127 -> 121; `corpus/baseline-metrics.tsv` is refreshed.

### Next step

The blocker is degenerate *input* to `Shell::extract`, not the T-junction
logic. Close the fallback by keeping the arrangement boundary clean as it is
built — no zero-length cut edges, no wire with a repeated vertex — so that
`sew` can hand back a shell `Shell::extract` accepts. Gate on the OpenSCAD
reference volumes above plus welded boundary edges, not on the old constants.

## Attempt: rebuild the arrangement wires (reverted)

`Shell::extract` was rejecting the sewn shell, so the obvious move was to make
`divide` emit wires that chain by *vertex object*, not just by welded index:
rebuild each half-edge as `Edge::new(&vertices[from], &vertices[to], curve)`.
That does remove the rejection — `NotClosedWire` disappears (99 `SameVertex` +
42 `NotClosedWire` + 17 `NotSimpleWire` becomes 16 + 10) — but it breaks the
geometry. In the viewer an entire outer wall of the snap vanishes and the
interior is exposed, and `opengrid_hull_cut` runs to a 120 s timeout.

The boolean log localises it. For `snap_one_clip`, subtracting the 6.66 mm3
horizontal cutter from a 3858.306 mm3 subject should leave 3851.645; the engine
returns 3765.926, i.e. it removes 92.4 mm3 — 14x the cutter's own volume. So it
is not "too many slivers": one whole face is trimmed away. That 86 mm3 deficit
is the entire volume error of the fixture.

Two corrections tried, both measured:

- Preserve `Edge::orientation` when rebuilding (`Edge::invert` only flips the
  flag, so a curve always runs `vertices.0 -> vertices.1`; rebuilding a
  reversed half as `(from, to)` with `orientation = true` claims the curve runs
  backwards). This removes the `hull_cut` hang and helps `snap_clip_cutout`
  a lot (58 -> 14 welded boundary edges) but leaves `snap_one_clip` at 1408.700
  and `snap_two_clips` at 1261.955.
- Rebuild only the edges the vertex weld actually touched, keeping the original
  edge object otherwise. This reproduces the checkpoint *exactly*
  (`snap_one_clip` 1504.7759163678484, identical to 13 decimals), so the
  rebuild never fires on these faces — the original `Edge` objects already
  carry the right endpoints.

Conclusion: rebuilding an edge that did not need rebuilding changes the result,
so the original edge objects carry state that `Edge::new` with a cloned curve
does not reproduce. The `NotClosedWire` rejections come from `sew`'s own vertex
weld, not from `divide`. Both variants are reverted; the engine is back at the
checkpoint above.
