# 2026-11-06 — diagnosing the snap's missing wall

Branch `diag/planar-divide`. The goal for this stretch was the red band the
viewer shows on the OpenGrid snap, which is a region of missing geometry.

## What the back-face overlay established

The viewer now paints a face whose normal points away from the eye red
(`4eec987`), the same convention as Blender's face-orientation overlay. On a
closed solid red therefore means a defect; on an open one it means you are
looking into the opening.

Two things had to be fixed before that reading was trustworthy:

- `4eec987` added the overlay itself. Both shaders shaded with
  `abs(dot(normal, light))`, so front and back were indistinguishable.
- `56c281d` fixed the analytic scene inverting revolution-surface normals.
  `flips_normal()` returned `false` for `Revolved`, so the flip resolved to
  `!face.orientation()` - but a revolution surface computes its normal outward
  from the axis while the tessellation winds the other way. A standalone
  cylinder *and* a difference's cavity wall both came out inverted, so a
  correctly cut hole was painted red. `cylinder_scene_matches_the_tessellated_mesh`
  never caught it because it compared ray distances, never normals.

After both, the mesh for the snap is:

    triangles=299  manifold=435  boundary=27  inconsistent=0

**No face is wound backwards.** Every red patch is a hole. The boundary edges
cluster in one band, `y -10.8..-12.4, z -1.2..-2.0`, which is the front wall.

## Where the wall goes

`sew`'s provenance (`ee70368`) records the outcome against the input faces, with
defect class, boundary count and bounds. Matching the hole's location:

    NotSimpleWire  boundary=105
    bounds [-6.000, -12.500, -7.000]..[6.000, -10.800, -0.800]

808 face records share it. The whole front-wall shell is rejected by
`Shell::extract`, so every face in it is lost - not a seam missing by a hair.

Dumping the offending wire showed it is traversed twice, out and back:

    0: e121 44->55  1.137     4: e145 44->55  1.137
    1: e132 55->58  0.844     5: e121 55->44  1.137
    2: e144 58->45  5.866     6: e84  44->45  4.263
    3: e84  45->44  4.263     7: e146 45->44  4.263

`3f15660` added `drop_wire_spikes`, which unwinds an edge followed by its own
reverse. Extract failures fell 40 -> 22 and welded boundary 27 -> 26 / 47 -> 45.

## Potential causes of the doubled wires — not yet investigated

`drop_wire_spikes` is a repair at the end of the pipeline. A wire that contains
each boundary edge twice means something upstream emitted it twice. Candidates,
roughly in order of suspicion:

1. **`split_boundary_edges` in `sew`.** It rewrites wires when splitting an edge
   at a new vertex, and an off-by-one in the insertion would duplicate a use
   rather than replace it.
2. **`merge_edges`.** It remaps every use through `edge_map`; if two distinct
   compressed edges merge into one, the two uses both survive pointing at the
   same edge, which reads as a doubled traversal.
3. **`divide` emitting both halves.** The planar fallback builds each face from
   the halves of the original edges; emitting both the pre-split and post-split
   form would produce exactly this.
4. **`apply_splits` in the classic path** doing the same thing on its own wires.
5. **Two coincident faces from different operands** each contributing the same
   boundary, so the seam contains both copies.

Telling these apart needs the wire dumped at every stage. `report_wire_defects`
already takes a stage tag and `BREPSCAD_DEBUG_SEW=1` prints `raw`, `weld`,
`merge1`, `split`, `merge2` and `final`, so the stage where the duplicate first
appears is one run away.

## The second defect class: pinch points

After the spike repair, the surviving wires are a different shape:

    12 -> 13 -> 17 -> 15 -> 14 -> 6 -> 0 -> 14 -> 12

Vertex 14 is visited twice, with the closed run `14 -> 6 -> 0 -> 14` hanging off
it. That is a pinch point, not a zero-area excursion - it encloses area, so it
must be kept. `split_wire_at_repeats` splits the inner run out as an additional
boundary of the same face, mirroring `c9ab63b`'s treatment of arrangement loops.

This does not yet change the output: extract failures stay at 22 and the four
fixture metrics are unchanged. Either the repaired shells then fail on a
further wire, or the split leaves a face whose second boundary the extract still
rejects. Worth checking before adding more repair passes.

## Caveats

- `left_boundary` counts edges used once in a shell, and `sew` also runs on
  intermediate half-shells where an open boundary is legitimate. Only `DROPPED`
  records are unambiguous.
- `report_wire_defects` runs at every stage, so counting `repeated face=` lines
  across the whole output overcounts - it includes the pre-repair stages.
  Count only `SEW-WIRES[final]` blocks.
- `opengrid_hull_cut` moved the wrong way under the spike repair (welded
  boundary 8 -> 14, volume 21430.08 -> 21430.63). A shell that now extracts can
  add open edges that were absent while it was discarded. Noted, not chased.

## Corrections - two mistakes worth not repeating

**A `--features` build overwrites the same binary.** `cargo build --release -p
brepscad --features provenance` writes `target/release/brepscad`, so a metrics
run after it silently measures a differently-compiled binary. Two figures
reported mid-session (one clip 1502.37, two clips 1462.74) came from that and were
never real. Always rebuild without features before measuring, and check the
binary's timestamp.

**A closed mesh is not a correct one.** `drop_degenerate_faces` - a filter keeping
only faces whose every wire had at least three edges - produced a mesh with
`boundary=0, inconsistent=0` and a volume of 559.51. That looked like a triumph
and was a flat plate: `sew` runs on the `and` and `or` halves, whose boundary
wires are partial and often short, so the filter deleted the walls. Bounds gave it
away (`z -6.8..-5.8`, a slab) and a screenshot made it obvious. It was reverted.

The lesson is to take a screenshot beside the numbers. The plate-versus-snap
difference was unmistakable in one image and invisible in every metric.

## Tooling added

- `BREPSCAD_DUMP_MESH=<prefix>` writes each mesh as OFF, which is what made the
  orientation and boundary checks possible.
- `--features provenance` plus `BREPSCAD_PROVENANCE=1` dumps the lineage of each
  face: which operation created it (with probe point and verdict), and which
  operation dropped it (with defect class and bounds).
- `BREPSCAD_DEBUG_SEW_LIMIT` raises the cap on how many defective wires are
  dumped; the default is 20, which is only about console noise.

## The method that worked: follow one face, not the totals

Everything above this point was aggregate measurement - face counts, volumes,
boundary totals - and it kept answering *that* faces were missing without saying
*where* they went. The step that broke the deadlock was tracing a single point
through the pipeline and dumping, at each stage, how many faces' bounds cover it.

`BREPSCAD_DEBUG_TRACE=x,y,z` does this. Each stage reports itself, including every
`?` that returns `None`, so the failure is named at the line that produces it
rather than inferred. Four levels deep, one run per level:

    point (0, -11, -1) in the missing band
      -> faces present in both operands (5 of 34, 2 of 66)
      -> BOOLEAN ATTEMPT Union @ 0.05/0.02/0.01 : EmptyOutputShell
      -> TRACE failed at create_loops_stores
      -> add_geom_vertex -> None
      -> curve_surface_projection failed, nearest point 0.073 away
      -> TRACE failed at altshell_to_shell
      -> intersection curve has 1 distinct point          <- the cause

## Three defects on that path, in the order they had to be fixed

**The two loops stores classified the same vertex independently.** `search_parameter`
decided `Front`/`Back`/`Inner` from the *polyline*, and `add_geom_vertex` re-derived
it from the *exact curve*. Wherever the two differ enough to move the parameter
across a range end, the polygon store cut an edge the geometry store only snapped
to, so its wire held one more edge and the next index past that point was off by
one. `add_geom_vertex` now returns a `Placement` (front, back, or cut) and
`apply_polygon_vertex` follows it, cutting at its own parameter since the two do
not share a parameterisation. This also uncovered a latent panic: the indices came
from the polygon store and were used to index the geometry store, which is now
bounds-checked.

**Decide before mutating.** `add_polygon_vertex` decided and mutated in one step,
so the polygon wire was cut before the geometry store knew about the vertex.
Splitting it into `find_polygon_vertex` (read-only) and `apply_polygon_vertex` lets
the sites run find -> geometry -> polygon, so both stores are updated from the same
indices.

**A degenerate intersection curve failed the whole pair.** `altshell_to_shell`
returned `None` for a leader polyline that deduped to a single point. A
zero-length curve carries no geometry, but refusing it discarded the pair and
every face in it - twelve times. It now passes through for the collapsed-edge pass
to remove.

## What remains, and why they are separate problems

**The snap's top face is missing.** The root boolean result is
`(3 shells, 195 faces, volume 1482.17)` with bounds reaching `z = 0.0`, so the
boundary is broadly right - but the OFF dump has *no triangle at all* near
`(0, -12, -0.05)`. The solid reaches the top and the mesh does not, which puts
this in tessellation rather than in any boolean: either the `z = 0` face is absent
and the bounds come from the walls, or it exists and its trim loop produces no
triangles. One measurement separates those.

**`opengrid_hull_cut` is untouched at 21430.63 against 23760.94.** It never
reaches the classic pair path, so none of the above applies. It is now the
largest single error (9.8%) and has had no attention.

## Caveat on the operation trace

`and`/`or` report how many of their result's faces cover the traced point, which
distinguishes "this half kept it" from "the other half did". But `face_covers`
tests **bounding boxes**, because `Face` does not expose its own bounds, so the
counts are loose: a face whose box spans the point counts even when its trim
excludes it. Read the counts as indicative and the mesh dump as precise.
